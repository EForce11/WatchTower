# Phase 1.5 — Core Decides, Kernel Flood Guard Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Remove every path by which an agent decides a response on its own, and replace it with one deliberately narrow exception: a kernel-level, per-source Flood Guard that runs in `audit` mode by default and reports every offender. Also make Core-signed `RATE_LIMIT` per source. Target: `v0.5.0`.

**Architecture:**
- The Reflex path is deleted end to end: the proto message, the engine handler, the safety limiter and the config.
- Turret accepts only `SignedCommand`s.
- The nftables table gains per-source meters (dynamic sets) and per-meter offenders sets, generated from a `FloodPolicy`. The kernel enforces them, and in `audit` mode no drop rules are installed for offenders.
- A small `flood` package polls the offenders sets and turns appearances and expiries into events, written to the log and to a bounded JSONL file. Phase 3 will forward them to Core.

**Tech Stack:** Go 1.26 (`CGO_ENABLED=0`), `github.com/google/nftables` (dynamic-set `expr.Dynset` with `expr.Limit`, `expr.Connlimit`), existing netns test harness (`unshare -Urn`, veth peers).

**Spec:** `docs/architecture.md` v3.3: Version History v3.3, §2.2–2.3, §3.1.3 (enforcement mode), §3.3.1/§3.3.4, §3.4 (origin table, §3.4.2 layout, §3.4.3 Flood Guard), §7 Phase 1.5, §9.

## Global Constraints

- Every binary builds with `CGO_ENABLED=0 go build ./...`. Production code never shells out.
- `golangci-lint` v1.64.8 stays clean, `make verify` passes, and the CI jobs in `docs/ci.md` stay green. Tests that skip for environment reasons use `internal/testenv.Skip`.
- Turret accepts **only** `SignedCommand`. Any other request (including an old `reflex` frame) gets `TURRET_RESULT_REFUSED_SAFETY` with detail `"unsigned requests are not accepted"`.
- Flood Guard modes are `off`, `audit` and `enforce`. **The default is `audit`.** In `audit` no Flood Guard rule drops a packet.
- Flood Guard defaults (spec §3.4.3): `syn_rate` 100/s, `syn_burst` 200, `pkt_rate` 5000/s, `pkt_burst` 10000, `conn_limit` 512, `block_for` 60 s.
- Allow rules stay first in the chain. No meter or offender rule may run before them.
- Flood Guard state never goes into `bans.json`, and it never shortens or touches the ban/perm/ratelim records.
- Per-source `RATE_LIMIT`: each `ratelim4/6` address gets its own `limit rate over 2/second burst 4 packets` bucket in a dynamic meter set (`rlmeter4/6`, timeout 60 s).
- Set and rule layout exactly as spec §3.4.2 v3.3, including the per-meter offenders sets `offsyn`, `offpkt` and `offconn` for IPv4 and IPv6.

## Review Focus

1. **A protected address under flood.** A peer in the allow set exceeds every threshold in `enforce`, and must still be accepted and must not appear in any offenders set (Task 3).
2. **Mode switch on restart.** Turret runs in `audit`, then restarts in `enforce` (or the reverse). The layout check must notice the difference and rebuild the table, and the bans must survive via `bans.json` (Task 3 and Task 5).
3. **Event file growth under a sustained flood from many sources.** `flood-events.jsonl` must stay bounded, rotating at 10 MiB and keeping one previous file. Event rate is bounded by sources, not packets (Task 4).
4. **An old Sentry still sends a `reflex` frame.** It must be refused cleanly, the connection must stay usable, and nothing may happen in the kernel (Task 1).
5. **Kernel without dynamic-set or connlimit support.** `Ensure` must fail with a clear error naming the missing feature, and must not silently install a partial guard (Task 3).

### Task 4: Offender watcher and event sink

**Files:** Create `internal/turret/flood/watch.go`, `events.go`, `watch_test.go`, `events_test.go`.

**Interfaces:**
- Consumes: `nft.Firewall.Offenders()`, `nft.Meter`, `config.FloodMode`.
- Produces:
  ```go
  type Kind string // "offender_started" | "offender_ended"
  type Event struct {
      Time      time.Time  `json:"time"`
      Kind      Kind       `json:"kind"`
      Meter     nft.Meter  `json:"meter"`
      Source    netip.Addr `json:"source"`
      Mode      config.FloodMode `json:"mode"`
      FirstSeen time.Time  `json:"first_seen"`
      LastSeen  time.Time  `json:"last_seen"`
  }
  type Sink interface { Write(Event) error }
  func NewJSONLSink(path string, maxBytes int64) (*JSONLSink, error) // rotates path -> path.1 at maxBytes, 0600
  type Watcher struct{ /* … */ }
  func NewWatcher(list func() ([]nft.Offender, error), mode config.FloodMode, sinks []Sink, log *slog.Logger, now func() time.Time) *Watcher
  func (w *Watcher) Poll() error                  // one diff step; exported for tests
  func (w *Watcher) Run(ctx context.Context, every time.Duration)
  const DefaultMaxEventFile = 10 << 20
  ```

- [ ] **Step 1: Write failing tests.** Use a fake `list` func and a fixed clock.
  - First `Poll` with `{syn, A}` → one `offender_started` event.
  - Same contents on the next poll → no event; `LastSeen` advances internally.
  - A disappears → `offender_ended` with first and last seen.
  - The same address under two meters → two independent lifecycles.
  - A `list` error → it is logged, no events are emitted, and the next successful poll diffs against the last good state, so no spurious ended/started pair appears.
  - Sink: JSON lines are parseable. After crossing `maxBytes` the file rotates to `.1` and a new file starts, with at most two files ever. Mode is 0600.
  - Flood of distinct sources: 10 000 sources in one poll → 10 000 started events written. The test asserts the rotation bound holds and memory per tracked source is O(1); the event rate is bounded by sources, not packets.
- [ ] **Step 2: Run** → FAIL. **Step 3: Implement.** A sink error is logged and does not stop the watcher; the slog sink is always present. **Step 4: Run** `go test -race ./internal/turret/flood/` → PASS. **Commit** (`feat(turret): flood offender watcher with bounded event log`).

## Phase 1.5 exit gate (spec §7)

- In the netns suite, a flood from one peer is **recorded but not dropped in `audit`** and **dropped in `enforce`**. A second peer and protected addresses are unaffected, entries expire after `block_for`, and per-source `RATE_LIMIT` throttles one peer without the other.
- No code path lets a non-signed request cause an action (`grep` check in Task 1 and the refusal tests).
- All CI jobs are green. The CHANGELOG and README are updated, and `v0.5.0` is tagged after merge.
